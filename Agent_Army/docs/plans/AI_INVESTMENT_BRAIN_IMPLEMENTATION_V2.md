## RALPLAN-DR Summary

### Principles (核心原则)

1. **市场即真理** - 股市结果是最终裁判，所有预测必须用市场验证
2. **数据驱动进化** - 从Phase 1开始积累经验，持续优化分析逻辑
3. **6维度综合决策** - 基本面、技术面、资金面、政策面、历史节点、行业面
4. **自我进化贯穿始终** - 不是等到Phase 3，而是从Phase 1就开始
5. **安全第一** - 设置参数边界和置信度阈值，防止过度优化

### Decision Drivers (决策驱动因素)

1. **数据可用性** - Tushare免费接口（daily、daily_basic）+ 降级策略
2. **技术可行性** - 历史节点分析AI分步实现，先验证后预测
3. **验证闭环** - 每个阶段都有可验证的输出，用市场结果验证

### Viable Options (可行方案)

#### Option 1: 渐进式实现（推荐）⭐
**描述**：分3个阶段实现，每个阶段都有可验证的输出，自我进化贯穿始终

**Pros**:
- 风险可控，每个阶段都有明确验收标准
- 可以先用免费接口，后续升级数据源
- 自我进化从Phase 1开始，不是等到Phase 3

**Cons**:
- 需要较长时间（5-8周）
- 需要多次集成和测试

**实施周期**：
- Phase 1（2-3周）：补齐4个缺失维度 + 启动经验积累
- Phase 2（1-2周）：6维度集成 + 启动参数优化
- Phase 3（2-3周）：完善自我进化系统

#### Option 2: 并行开发（修订）
**描述**：同时启动多个Agent并行开发所有缺失模块

**Pros**:
- 速度最快（2-3周）

**Cons**:
- 需要大量API资源（当前余额不足）
- 集成复杂度高，6维度决策逻辑难以协调
- 测试困难，问题定位难

**可行性分析**：
- ⚠️ 当前API余额不足，无法启动多个Agent
- ⚠️ 历史节点分析AI技术可行性未验证，并行开发风险大

#### Option 3: 最小可行产品（修订）
**描述**：只实现最核心的"选股"功能，暂不实现监控验证和自我进化

**Pros**:
- 快速上线（1-2周）
- 资源消耗少

**Cons**:
- ❌ 无法形成闭环，不符合deep-interview的核心需求
- ❌ 缺少验证环节，无法确认预测准确性
- ❌ 无法自我进化，违背"AI投资外脑"的定位

**可行性分析**：
- ❌ 不符合"自我进化"原则
- ❌ 无法验收：无法验证"6个核心指标"的准确性

### Recommended Approach

**选择 Option 1：渐进式实现（修订版）**

**理由**：
1. ✅ 符合所有核心原则
2. ✅ 每个阶段都有量化验收标准
3. ✅ 自我进化贯穿始终
4. ✅ 降低技术风险（历史节点分析AI分步实现）
5. ✅ 符合当前资源限制

### Phase 1: 补齐缺失维度 + 启动经验积累（2-3周）

#### 1.1 历史节点分析AI ⭐ **最重要，分3步实现**

**优先级**：🔴🔴🔴🔴🔴（最高）

**位置**：`src/agents/business/stock/historical_node_ai.py`

**修订方案**：分3步渐进实现

**Step 1: 历史统计分析**（Phase 1.1，2天）
- 功能：统计历史事件的发生时间、频率
- 输入：股票代码、历史K线数据、历史事件列表
- 输出：事件统计报告（如："3月份政策发布频率最高"）
- 数据源：Tushare `daily`（免费）
- 验收标准：
  - [ ] 使用中国电建近3年数据，能够统计政策发布频率
  - [ ] 生成统计报告，包含：事件类型、发生频率、时间分布
  - [ ] 单元测试通过率≥90%

**Step 2: 周期性验证**（Phase 1.2，3天）
- 功能：验证历史周期性规律是否真实存在
- 输入：历史统计数据、验证时间范围
- 输出：周期性验证报告（如："政策发布周期为12个月，置信度75%"）
- 数据源：历史数据回测
- 验收标准：
  - [ ] 使用中国电建近3年数据，验证政策发布周期性
  - [ ] 周期性预测准确率≥70%，误差在±1月内
  - [ ] 生成验证报告，包含：周期长度、置信度、误差分析
  - [ ] 单元测试通过率≥90%

**Step 3: 周期性预测**（Phase 1.3，2-3天）
- 功能：基于验证后的周期性规律，预测未来事件
- 前置条件：Step 2验证通过（置信度≥70%）
- 输入：历史周期规律、当前时间
- 输出：周期性预测报告（如："下次政策发布可能在2026年3月"）
- 验收标准：
  - [ ] 预测下次事件时间，误差在±1月内
  - [ ] 生成预测报告，包含：预测时间、置信度、风险提示
  - [ ] 单元测试通过率≥90%

**降级策略**：
- 如果Step 2验证失败（置信度<70%），则不执行Step 3
- 改用技术面分析替代历史节点分析

        actual_buy_price: float  # 实际买入价

### Phase 2: 6维度集成 + 启动参数优化（1-2周）

#### 2.1 综合决策AI（新增：决策优先级）

**位置**：`src/agents/business/decision/comprehensive_decision_ai.py`

**核心功能**：
1. **6维度数据聚合**
   - 收集6个维度的分析结果
   - 数据标准化处理
   - 权重配置

2. **综合评分模型**
   - 多维度加权评分
   - 置信度计算
   - 风险评估

3. **6个核心指标生成**（新增：决策优先级）
   - 割肉价（止损线）- **最高优先级，必须遵守**
   - 买入价（入场点）- **基于技术面**
   - 持仓成本（预期）- **基于买入价区间**
   - 压力位（阻力位）- **基于技术面**
   - 主升浪时间窗口 - **基于历史节点**
   - 目标价 - **基于基本面估值**

**决策优先级**（新增）：
```
当6维度给出矛盾信号时，按以下优先级决策：

Level 1: 割肉价（止损线）- 最高优先级，必须遵守
Level 2: 基本面 - 通过筛选（PB<1, ROE>10%, 负债率<60%）
Level 3: 技术面 - 择时（突破支撑位、成交量放大）
Level 4: 资金面 - 确认（主力资金流入）
Level 5: 政策面 - 加权（政策支持提高权重10%）
Level 6: 历史节点 - 参考（不作为主要决策依据）

冲突示例：
- 基本面好 + 技术面差 → 等待技术面改善
- 基本面差 + 技术面好 → 不参与（基本面是底线）
- 政策支持 + 资金流出 → 谨慎参与（降低仓位）
```

**验收标准**（修订版）：
- [ ] 能够生成包含6个核心指标的完整报告
- [ ] 6个指标在合理范围内（割肉价<买入价<目标价）
- [ ] 决策时间<30秒
- [ ] 单元测试通过率≥90%
- [ ] 使用中国电建进行端到端测试

## ⚠️ 风险控制（修订版）

### 技术风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 历史节点分析AI无法实现 | 无法完成核心功能 | 分3步实现：统计→验证→预测，如果验证失败则改用技术面分析 |
| 数据权限不足 | 高级数据无法获取 | 使用降级策略（成交量替代资金流向）|
| 自我进化过拟合 | 系统性能下降 | 设置参数边界，每次调整<10% |
| API余额不足 | 无法并行开发 | 采用手动实现，不用Agent |

### 业务风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 预测不准确 | 用户信任度下降 | 强调"市场即真理"，不承诺准确率 |
| 数据质量差 | 分析结果不可靠 | 数据清洗、异常值处理 |
| 决策冲突 | 无法生成6个指标 | 明确决策优先级，基本面是底线 |
