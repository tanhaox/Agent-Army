## 🎯 系统职责

立项会 = **启动器**，不是审核器。

它的本质是：**在写第一个字之前，把设定库打磨到没有内部瑕疵**。

"立项会反复打磨一周几十轮"——这是用户的**最高纲领**，打磨不过就**别写**（因为未来 1-2 年的写作投入远大于立项会成本）。

---

## 📋 输入与输出

### 输入

- `books/<name>/settings/` 6 维度设定
- `books/<name>/timeline.md` 故事时间线
- `books/<name>/voice-prints/*.md` 角色声音指纹
- `books/<name>/meta.md` 一句话简介 + 受众 + 基调

### 输出

立项会报告写入 `books/<name>/kickoff_report.md`，**至少包含**：

1. ✅ **通过项**：已检查 + 已对齐
2. ⚠️ **冲突清单**：必须解决的内部冲突
3. ❌ **否决项**：立项级别不能通过的硬伤
4. 🔄 **返设定项**：哪些字段需要重新填写
5. 📊 **多 Agent 视角报告**：每个 Agent 的独立报告 + 问题汇总

## 🚦 立项会流程

### Phase 1：状态进入

- 作者完成 6 维度设定填写
- 系统自动检测"Step 1 完成"信号
- 自动触发立项会（无需作者命令）

### Phase 2：多 Agent 协同审查（云端）

- 调用 `multi-agent-cloud.md` 的 4-6 个 Agent persona
- 每个 Agent 输出独立报告
- 合并为"问题汇总"（Q33 决策）

### Phase 3：冲突识别与分级

系统按问题严重度分 4 级：

| 级别 | 含义 | 处理 |
|------|------|------|
| 🔴 **硬否决** | 设定本身有致命矛盾（如主角金手指与世界观规则冲突） | 不通过立项 |
| 🟠 **必须修复** | 设定内部不一致，需返设定阶段 | 列出必填修复项 |
| 🟡 **建议改进** | 可接受但有更优解 | 作者可选择改进 |
| 🟢 **已对齐** | 通过，多 Agent 一致认可 | 报告存档 |

### Phase 4：作者决策

- 作者阅读立项会报告
- 选择：
  - **A. 通过**：进入 Step 2（章节规划）
  - **B. 返设定**：修复冲突项 → 重新立项会（增量模式）
  - **C. 强行通过**：跳过立项会（**仅在"强制本地模式"开启时允许**）

### Phase 5：立项会状态记录

- `meta.md` 加 frontmatter：`kickoff_passed: true / false`
- `kickoff_report.md` 永久归档
- 每次返设定都生成新版本 `kickoff_report_v2.md`

## 📝 必须解决的冲突类型清单（7 类）

立项会必须**至少检查**这 7 类冲突：

### 1. 一句话简介 vs 6 维度的内在一致性
- 例：简介说"现代程序员穿越修仙界"，但世界观没写"修仙界规则"——内部不一致

### 2. 主角设定 vs 看点（受众期待）
- 例：主角设定是"普通少年成长"，但看点写"硬核修炼 + 智斗"——风格错位

### 3. 金手指 vs 世界观边界
- 例：金手指是"无限刷怪"，但世界观边界规定"打怪有冷却"——自我矛盾

### 4. 核心冲突 vs 主角目标/执念
- 例：核心冲突是"主角揭穿阴谋"，但主角目标是"修炼成仙"——目标与冲突不挂钩

### 5. 人物关系网 vs 人物弧光
- 例：反派动机是"对主角的恨"，但反派与主角之前没有任何交集——动机无源

### 6. 时间线 vs 角色出场年龄
- 例：第 5 章主角 18 岁，但人物档案写"主角 7 岁开始修炼"——修炼时长与年龄不匹配

### 7. 伏笔回收 vs 总章数
- 例：埋了 8 个伏笔，每个需要 20+ 章回收，但总章数仅 50——回收密度过大

## 🤖 多 Agent 视角（云端）

具体协议见 `multi-agent-cloud.md` §三。这里只列标配 4-6 个 Agent persona：

| Agent | 视角 | 重点审查 |
|-------|------|---------|
| **档案 Agent** | 设定完整性视角 | 字段是否齐全、是否符合模板 |
| **世界观 Agent** | 世界规则视角 | 世界观规则的内在一致性 |
| **人物 Agent** | 人物行为视角 | 性格 / 动机 / 弧光自洽性 |
| **节奏 Agent** | 故事结构视角 | 起承转合 / 高潮分布 |
| **读者 Agent** | 受众期待视角 | 看点 vs 受众期待对齐 |
| **金手指 Agent** | 设定利用视角 | 金手指用法 / 限制 / 升级 |

**注意**：MVP 阶段先实现前 4 个，剩下 2 个 Phase 2 补。

## 🔄 增量模式 vs 全量模式（Q30 决策）

- **默认增量**：返设定时，立项会**只审查修改的字段及其连带影响**
- **手动切全量**：作者可强制全量重审（每次 P10 决策变更、或新发现重大冲突时）

具体实现：

```yaml
# kickoff_meeting 命令参数
mode: increment | full   # 默认 increment
since: <chapter_or_time> # 自 X 章节以来变动的字段
force: true | false       # 强制全量
```

## 🔴 立项会的强制 / 退出机制

### 强制触发场景

| 场景 | 触发 |
|------|------|
| 作者填完 6 维度设定 | 自动 |
| 作者修改 6 维度设定中的任一字段 | 自动（增量） |
| 作者修改主角核心设定 | 自动（全量，必须返设定） |
| 作者修改世界观的根本规则 | 自动（全量） |
| Phase 3 跨章审核累计出 5+ 🔴 冲突 | 建议触发 |

### 作者可强行跳过的条件

- **仅在作者主动开启"强制本地模式"** 时（写作中）
- 跳过时 meta.md 必须记录 `kickoff_skipped: true`
- 跳过累计 3 次后**警告作者**："你的设定正在积累技术债"

## 🧪 测试用例（MVP 必过）

1. **空白书立项会**：作者完全没填，应能跑通但报告"无设定"
2. **冲突书立项会**：作者故意写"金手指 = 飞"，但世界观写"无飞行能力"——必须报错
3. **完美书立项会**：所有 7 类冲突都无——必须给绿灯
4. **增量立项会**：作者修改人物名字，重新立项——必须只审查相关字段
5. **作者强行跳过**：记录 skip 状态、警告累计
